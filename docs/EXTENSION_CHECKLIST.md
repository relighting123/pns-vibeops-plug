# 에이전트·툴·스킬 추가 개발 체크리스트

## 먼저 무엇을 추가하는지 결정

| 필요 | 추가 대상 | 구현 내용 |
|---|---|---|
| 작업 방법을 재사용 | 스킬 | SKILL.md와 필요한 참고자료·스크립트 |
| 독립된 담당자와 문맥 | 에이전트 | 역할·입출력·호스트별 정의·배분 규칙 |
| 현재 도구로 할 수 없는 실행 | 툴 | 실행 코드 또는 MCP 연결·입출력·오류 처리 |

스킬이 도구 이름을 언급하는 것만으로 새 도구가 생기지 않는다. 에이전트 파일만 추가해도 자동 배분이 보장되지 않는다. 호출 주체와 완료 조건까지 연결한다.

## 1. 에이전트 추가

| 체크 | 개발할 것 | 현재 저장소 위치/작업 |
|---|---|---|
| [ ] | 역할·사용 조건·업무 경계 | 역할 이름, 언제 배정할지, 맡기지 않을 업무 정의 |
| [ ] | 입력 계약 | 목표, 요구사항 ID, 관련 자료, 담당 경로, 기준 커밋, 완료 조건 |
| [ ] | 결과 계약 | 변경 파일, 커밋, 실행 검사와 결과, 근거, 차단 요소, 다음 행동 |
| [ ] | Claude 정의 | agents/이름.md: name, description, tools, 본문 |
| [ ] | Codex 정의 | .codex/agents/sdlc-이름.toml: name, description, developer_instructions |
| [ ] | 호출 연결 | skills/vibeops-orchestrate-sdlc/SKILL.md에서 배정 조건과 사용할 역할/스킬 설명 |
| [ ] | 호스트 차이 | Codex TOML은 대상 프로젝트 .codex/agents에 설치. 자동 배포로 오해하지 않도록 안내 |
| [ ] | 병렬 작업 | 파일 소유권, 의존성, worktree 필요성, 결과 통합 순서 정의 |
| [ ] | 권한 | 필요한 도구만 지정. 지침은 실제 OS 권한을 대체하지 않음 |
| [ ] | 검증 | 필수 키 파싱, 역할 개수 기대값, 실제 호출·핸드오프·실패 시나리오 확인 |
| [ ] | 문서 | 개발가이드의 역할 표와 설치 설명 갱신 |

예: 위키 연구 담당자를 추가한다면 질문과 대상 버전을 입력받고, 출처·적용 범위·불확실성을 반환한다. 검색 스킬을 활용하며 소스 구현 권한을 자동으로 줄 필요는 없다. 현재는 vibeops-search-wiki 스킬만 제공하므로 기존 담당자가 직접 검색한다.

## 2. 툴 추가

### A. 기존 호스트 도구로 가능한 경우

- [ ] 파일 검색·편집·Git·터미널 기능을 먼저 확인한다.
- [ ] 새 툴을 만들지 않고 스킬에 입력·명령 사용법·출력 해석을 정의한다.
- [ ] 호출 경로와 작업 디렉터리를 명시한다.

### B. 로컬 보조 스크립트가 필요한 경우

- [ ] 명령 인자, 표준 출력(JSON 등), 표준 오류, 종료 코드, 타임아웃 규칙을 정한다.
- [ ] 입력 검증, 경로 제한, 오류 처리, 반복 실행 시 동작을 구현한다.
- [ ] 파일·외부 상태를 바꾸는 기능은 변경 범위와 실패 후 복구 방법을 명시한다.
- [ ] 셸 문자열 결합 대신 인자 배열을 사용하고 자격증명을 로그에 출력하지 않는다.
- [ ] 필요한 언어·라이브러리·OS 의존성을 문서화한다.
- [ ] 스킬에서 스크립트 위치, 실행 시점, 결과 해석과 실패 시 행동을 연결한다.
- [ ] 정상 입력·빈 결과·잘못된 입력·실패·재실행을 검증한다.

스크립트는 특정 작업을 수행하고 종료하는 도구다. 모델 호출·에이전트 스케줄링·상시 루프를 넣어 런타임으로 확대하지 않는다.

### C. 외부 서비스 MCP 도구가 필요한 경우

- [ ] 기존 승인된 서버/연결에 필요한 기능이 있는지 확인한다.
- [ ] 서버 주소, 인증 주체, 접근 범위, 노출할 도구를 확정한다.
- [ ] 새 서버를 구현해야 한다면 입력 스키마, 출력 스키마, 오류 응답, 타임아웃, 재시도 정책을 개발한다.
- [ ] 읽기와 쓰기 기능을 구분하고 실제 호스트의 권한 정책에 연결한다.
- [ ] 자격증명은 환경 또는 호스트의 비밀 관리에 보관한다.
- [ ] Codex·Claude 각각의 지원 설정 형식으로 연결한다. 존재하지 않는 URL이나 키를 기본 번들에 넣지 않는다.
- [ ] 스킬에 실제 도구의 검색·호출 방법과 연결 불가 시 대안을 명시한다.
- [ ] 인증 실패·권한 부족·서비스 장애·빈 결과·중복 쓰기 방지를 검증한다.
- [ ] docs/MCP.md에 설정과 운영 방법을 기록한다.

현재 저장소에는 MCP 서버 구현이 없다. 외부 연결 추가는 서버/인증이 정해진 뒤 수행한다.

## 3. 스킬 추가

| 체크 | 개발할 것 | 파일/방법 |
|---|---|---|
| [ ] | 호출 조건 | 어떤 요청이나 실패 상황에서 사용할지 description에 작성 |
| [ ] | 원본 | skills/스킬명/SKILL.md 생성. name과 description 머리말 작성 |
| [ ] | 절차 | 입력 확인 → 단계별 행동 → 결과 확인 → 실패 대응 → 반환 형식 |
| [ ] | 완료 조건 | 실제 파일·검사·근거 등 확인 가능한 조건 |
| [ ] | 참고자료 | 필요한 경우 같은 스킬 아래 references/에 배치하고 상대 경로 연결 |
| [ ] | 실행 도구 | 기존 도구를 사용하거나 필요한 보조 scripts/를 구현 |
| [ ] | 흐름 연결 | vibeops-orchestrate-sdlc 또는 담당 에이전트가 언제 새 스킬을 읽을지 정의 |
| [ ] | 문맥 절약 | 관련 자료만 단계적으로 읽도록 작성. 위키 전체 주입 금지 |
| [ ] | 패키지 갱신 | git diff --check 실행 |
| [ ] | 구조 확인 | tests/test_plugin.py의 스킬 개수 기대값과 패키지 일치 검사 갱신 |
| [ ] | 실제 동작 확인 | 호출되어야 할 요청·호출되면 안 되는 요청·실패/재개 사례 확인 |
| [ ] | 배포 문서 | 설치 안내, 변경 설명, 필요한 매니페스트 버전 갱신 |

## 4. 공통 완료 기준

- [ ] 원본과 양쪽 플러그인 사본이 일치한다.
- [ ] 새 파일의 호출 주체와 경로가 연결되어 있다.
- [ ] 현재 호스트가 지원하지 않는 기능을 자동 지원한다고 표기하지 않는다.
- [ ] 실제 실행하지 않은 검증을 통과했다고 쓰지 않는다.
- [ ] 변경 파일·기능·검증 결과·미검증 범위를 PR에 기록한다.

현재 단위 테스트는 구조·훅 출력 검사다. 스킬을 모델이 일관되게 따르는지와 호스트 설치 성공은 별도 실행 확인이 필요하다.

읽기·변경 스킬과 공통 import 구조는 [공용 데이터 접근](DATA_ACCESS.md), 용어와 이름은 [명명 규칙](NAMING.md)를 따른다.
