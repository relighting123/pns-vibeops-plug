# 지식 운영 가이드

| 종류 | 관리 위치 | 조회 기준 |
|---|---|---|
| 프로젝트 | 대상 프로젝트의 OpenWiki와 코드·테스트 | 구현 및 구조 |
| 공용 | PNS VibeOps Wiki의 `sources/`와 생성된 `openwiki/` | 공통 계약 및 운영 규칙 |
| 플러그인 | 이 레포의 skills, references, wiki | 기능 실행 절차와 [ITSM 대상 시스템별 GitLab 연결표](../wiki/ITSM-GitLab-Mapping.md) |
| 개인 | 사용자 로컬 메모 | 사용자가 요청한 개인 경험 |

기본 공용 저장소 주소는 `config/shared-knowledge.json`에 있다. `SDLC_WIKI_URL`을 직접 설정한 PC에서는 새 주소 `https://github.com/relighting123/pns-vibeops-wiki.git`로 갱신한다. `SDLC_WIKI_LOCAL`을 사용하면 해당 체크아웃의 `origin` 주소도 새 주소로 갱신한다. 공용 규칙은 공용 레포에서 관리하고 소비처에는 출처를 연결한다. 질문에 맞는 범위를 먼저 검색하고 필요한 절만 읽는다. 공용 캐시는 발행 브랜치와 비교하며 답변에 사용한 커밋을 남긴다. 최신 확인 실패 시 이전 커밋을 사용했다는 사실을 표시한다. 벤치마크는 동일 공용 커밋을 고정한다.

문서 반영은 `vibeops-update-shared-wiki` 절차를 따른다. PDF 페이지, 원본 링크·버전, 적용 범위, 시행일, 담당자를 기록한다. 같은 규칙은 기존 문서를 수정하고 상충하는 원본은 검토 항목으로 남긴다. `sources/` 변경과 OpenWiki 생성 결과를 같은 PR/MR에 올린다. 수치·예외·근거가 유지됐는지 확인한 후 발행한다. 발행 검증은 대표 질문의 답과 인용, 커밋으로 확인한다. 생성물에 오류가 있으면 원본을 수정해 다시 생성한다.

## 공용 규칙 개정 실습

Cube 조회 운영 문서의 재시도 한도가 변경됐다고 가정한다. 발행 브랜치에서 docs/cube-retry-policy 작업 브랜치를 만든다. sources/systems의 기존 Cube 문서에 이전과 새 한도, 적용 대상과 시행일, 원본의 페이지 및 버전을 기록한다. 동일 범위의 프로젝트 설명에는 공용 문서 경로를 연결하고, 실제 구현을 바꿔야 하면 별도 코드 PR을 연결한다.

OpenWiki 초기화 또는 갱신을 수행한 뒤 생성된 관련 절에서 수치·예외·근거가 모두 유지됐는지 검토한다. 지식 담당자는 원본과 생성 diff를 함께 승인하고, 발행 후 해당 커밋을 로컬에 갱신해 대표 질문의 답과 인용을 확인한다. 이전 값을 답하면 브랜치, 커밋, 캐시 상태와 인용 절을 차례로 점검한다. 잘못 발행했다면 발행 브랜치에 수정 또는 되돌리기 PR을 올리고 새 커밋으로 재검증한다.

예제 기록은 「시행일 2026-12-01 / Cube 조회 전용 / 원본 운영 가이드 v3 12쪽 / 담당 서비스 운영팀」처럼 작성한다. 값과 날짜는 실습용이다. 개인 메모는 작성자가 공유 가능한 부분을 지정하고 근거와 적용 범위를 확인한 뒤 공용 변경의 입력으로 사용한다.
