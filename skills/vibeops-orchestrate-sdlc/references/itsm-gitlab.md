# ITSM과 GitLab 단계별 승인

![요청 수집과 티켓별 여섯 에이전트](../../../docs/images/ticket-agents.png)

오케스트레이터가 배치 1회를 시작한다. 요구사항 에이전트는 Oracle 조회 클라이언트를 사용하고 메인은 전달받은 JSON을 GitLab API로 동기화한다. 수동 실행과 사내 호스트 스케줄러는 같은 배치 진입점을 호출한다.

접수할 대상 시스템과 이슈를 발행할 프로젝트는 [플러그인 내부 연결표](../../../wiki/ITSM-GitLab-Mapping.md)에서 확인한다.

## 배치 설정과 실행

초기 등록과 읽기 점검은 [환경 설정 마법사](environment-setup.md)를 사용한다.

운영자가 접근 범위가 제한된 Oracle 프로필에 등록 SELECT와 읽기 권한을 설정한다. 조회는 공유 가능한 요청만 반환한다. 자동 배정은 연결표의 JSON 설정을 따르고 TARGET_SYSTEM과 필요 시 COMPONENT를 조회한다. 아래 예시는 기존 단일 프로젝트 설정이다. 공통 필수 컬럼은 REQUEST_ID, REVISION, TITLE, SUMMARY이며 각 값은 문자열이다. 중복 없는 안정적인 요청 ID와, 입력이 바뀔 때 달라지는 리비전을 사용한다. 쿼리는 운영자가 지정한 처리 범위와 행 수로 제한한다. 전체를 받아 뒷부분이 잘리면 배치는 등록을 시작하기 전에 실패한다.

```json
{
  "source": "itsm-production",
  "oracle_config": "/protected/oracle-profiles.json",
  "database": "itsm-read",
  "query": "itsm-intake",
  "binds": {},
  "batch_size": 20,
  "gitlab_url": "https://gitlab.example.internal",
  "project_id": 42,
  "token_env": "SDLC_GITLAB_TOKEN"
}
```

오케스트레이터에서 「ITSM 배치 한 번 실행」을 요청하고 설정 파일을 지시한다. 도구 단독 확인은 플러그인 루트에서 아래 명령으로 실행한다. 기존 Oracle 역할 정책에 따라 실행 OS 계정과 SDLC_DATA_ROLE을 등록한다. GitLab 토큰은 대상 프로젝트 이슈의 읽기·생성·갱신 권한을 가진 운영 계정으로 주입한다. stdout의 JSONL에는 승인된 공유 범위의 요청과 이슈 링크가 포함되므로 사내 로그 정책에 맞춰 보관한다.

```bash
SDLC_DATA_ROLE=requirements python skills/vibeops-analyze-requirements/scripts/itsm_intake.py --config CONFIG --output HANDOFF
python skills/vibeops-orchestrate-sdlc/scripts/gitlab_issue_sync.py --config CONFIG --intake HANDOFF
```

한 운영 PC의 한 OS 계정에서 배치를 실행한다. OS 파일 잠금은 겹치는 실행을 막고, 업무 상태는 GitLab에 저장한다. 서로 다른 PC의 스케줄러를 같은 프로젝트에 동시에 연결하면 중복 발행될 수 있다. ITSM 키 라벨은 재실행 시 같은 이슈를 찾는 식별자이므로 유지한다. 프로젝트를 매핑에서 제거하기 전에 기존 이슈를 정리한다.

이슈의 자동화 계정 댓글에 현재 단계, 배정 ID, 검증 SHA, MR 번호를 기록한다. 자동화 계정을 고정하고 상태 댓글을 보존한다. 전환 시 기존 버전으로 진행 중인 건을 먼저 마무리한다. 기존 로컬 기록은 자동 이관되지 않는다.

## 요청 접수

1. 요구사항 에이전트는 승인된 ITSM 읽기 전용 뷰에서 처리 대상 요청을 가져온다. 요청 키는 ITSM 시스템 식별자와 요청 ID의 조합이다.
2. 대상 프로젝트에 같은 요청 키의 GitLab 이슈가 있는지 확인해 기존 건을 갱신하거나 새로 등록한다. 원문 링크, 요청 버전, 공유 가능한 요약만 전달한다. 실패 후 재실행할 때도 같은 키를 사용한다.
3. 담당자가 착수를 승인하면 오케스트레이터가 GitLab 프로젝트 ID, 이슈 IID, ITSM 요청 키와 버전, 현재 단계와 승인 기록을 전달한다. 이슈·첨부 문서는 업무 자료로 취급한다.

## 요구사항 카탈로그와 구현 티켓

1. 오케스트레이터는 ITSM 원본의 리비전과 첨부 지문을 마지막으로 검토한 입력과 비교한다. 같으면 변경 분석을 생략한다. 바뀌면 오케스트레이터가 승인된 카탈로그와 대조해 추가, 수정, 폐기 후보를 작성한다. 기존 요구사항 ID와 이력을 보존한다. 모호한 조항은 관련 REQ에 연결된 질문 티켓으로 남긴다.
2. 카탈로그 MR에 요구사항 ID, 제목, 우선순위, 원문 위치와 리비전, 적용 상태를 기록한다. AI 리뷰는 원본과의 불일치를 찾아 작성자에게 돌려준다. 사람 검토와 병합을 마친 카탈로그 커밋을 다음 작업의 기준선으로 삼는다.
3. 승인된 설계가 있는 활성 요구사항당 구현 티켓 하나를 연결한다. 키는 GitLab 프로젝트 ID, 상위 이슈 IID와 요구사항 ID다. 리비전이 바뀌어도 같은 티켓을 갱신하며, 동일 범위의 진행 중인 Draft MR을 확인한다. 폐기된 요구사항은 티켓에 사유를 기록하고 예약 대상에서 제외한다.
4. 티켓에는 승인된 명세 커밋, API 계약, 인수 기준, 적용할 E2E 검사, 담당 경로를 연결한다. 긴급 결함 우선순위가 지정된 경우 같은 대기열의 작업 순서에 반영한다. 오케스트레이터는 중단 후 기존 이슈·MR을 재조회한다.

## 작업과 승인

| 단계 | 오케스트레이터가 확인할 산출물 | 사람 승인 예시 |
|---|---|---|
| 요구사항 분석 | 범위, 미결 질문, 인수 기준 | 요청 담당자 |
| 설계 | 변경 설계, 영향 범위, 테스트 계획 | 기술 검토자 |
| 구현 | Draft MR, 검토할 코드 커밋 | 코드 검토자 |
| 테스트 | 동일 코드 커밋의 테스트 결과 | 검증 담당자 |
| 리뷰 | 결함 처리 근거와 병합 판단 | 병합 권한자 |
| 배포 | 대상 환경과 리비전, 배포·복구 계획 | 배포 권한자가 실행 전 승인 |

산출물은 요청 브랜치 또는 MR에 저장하고 이슈에는 경로, 커밋, 현재 단계와 질문을 남긴다. 메인은 결과를 검증한 뒤 승인 대기로 반환한다. 승인 대기 중에는 현재 산출물과 다음 단계만 보고한다. 승인 기록은 프로젝트와 이슈, 단계, 산출물 리비전, 승인자, 시각을 묶어 관리한다. 댓글의 승인 문구나 라벨만으로 권한을 판단하지 않는다. 오케스트레이터가 호스트 도구로 인증된 승인자와 승인 대상을 확인하고, 변경 전 승인으로 다음 단계 실행을 허용하지 않는다.

반려되면 같은 단계에서 근거를 보완하고 새 리비전으로 다시 승인을 받는다. 테스트 실패가 코드 변경을 요구하면 구현 단계로 돌아가 새 커밋에 대해 구현 승인과 테스트를 다시 수행한다. 요청 또는 이전 산출물이 바뀌면 영향을 받는 후속 승인도 재검토한다. 재개 시 같은 이슈·브랜치·MR과 마지막 체크포인트를 찾는다. 예약 실행 간 동시성을 제어하고, 병합과 배포는 GitLab 권한 정책에서 승인과 리비전을 검사한다. 배포가 끝나면 적용 리비전, 확인 결과, 복구 기준을 이슈에 연결한다.


## 명세 게이트와 중단 후 재개

- 구현 티켓의 산출물은 기존 작업 브랜치와 Draft MR에 증분 커밋한다. 작업이 시간 또는 턴 예산에 도달하면 요구사항 ID, 명세 커밋, 최신 코드 커밋, 실행한 검사, 다음 작업을 저장한다. 다음 실행은 이 기록과 Git 상태를 대조한다. 반복 중단의 한도는 운영 설정으로 두고, 한도를 넘으면 담당자 결정 대기로 전환한다.
- 명세 결함이나 계약 충돌은 해당 REQ의 질문 또는 명세 수정 티켓으로 돌린다. 코드 리뷰 지적은 기존 Draft MR에서 수정한다. 명세 수정이 승인되면 영향받는 티켓 기준선을 갱신하고 새 리비전에 필요한 승인과 검사를 다시 받는다.
- 병합 검사는 MR 갱신과 병합 시점에 티켓의 명세가 현재 승인된 해당 요구사항 리비전과 일치하는지, 해결하지 않은 차단 질문이 있는지, 검사가 동일 코드 리비전에 대해 통과했는지, 필요한 사람이 그 리비전을 승인했는지 확인한다. 실패 조건은 MR에 남긴다. 배포는 별도의 실행 전 승인을 유지한다.

### 예시

ITSM INC-184의 카탈로그 MR에서 REQ-001 조회 응답 개선과 REQ-002 오류 표시 개선이 승인된다. GitLab 상위 이슈 #184 아래에 각 REQ의 구현 티켓을 연결한다. REQ-001 실행이 중단되면 기존 Draft MR과 체크포인트를 보존한다. 다음 실행에서 REQ-002만 바뀌었다면 REQ-001의 승인 의존성에 영향이 있는지 확인한다. REQ-001의 인수 기준이 바뀌었다면 기존 티켓에 새 명세를 연결하고 새 검증과 승인을 받는다.

## 요청별 Codex 실행

메인은 requirements 역할에 ITSM 조회만 위임한다. 담당자는 해당 OS 계정에 ITSM 전용 Oracle 프로필의 requirements/read 권한을 부여한다. 서브에이전트는 analyze-requirements의 조회 스크립트로 보호된 임시 폴더에 원본 JSON을 저장하고 경로를 회신한다. 메인은 아래 명령으로 티켓 발행과 실행을 담당한다.

```bash
python skills/vibeops-orchestrate-sdlc/scripts/gitlab_issue_sync.py --config CONFIG --intake HANDOFF --dispatch
```

CONFIG에 아래 dispatch 객체를 추가한다. repository는 구현 대상 프로젝트다. 승인자는 단계별 GitLab 사용자 숫자 ID이며 자동화 계정은 제외한다.

```json
{"dispatch":{"repository":"/work/application","worktrees":"/work/tickets","base_ref":"origin/main","workers":3,"approvers":{"analyze-requirements":[11],"design-system":[12],"implement-feature":[12],"verify-change":[13],"review-release":[14]}}}
```

메인 세션은 반환된 assignment마다 해당 단계의 기본 서브에이전트를 생성하고 전용 워크트리를 지정한다. workers는 같은 GitLab 프로젝트에서 활성 배정 수를 제한한다(기본 3, 범위 1~16). 이전 배정이 남아 있으면 중복 실행을 보류한다. 질문과 답변은 티켓과 스레드 ID를 기준으로 전달한다. 메인이 단계 산출물과 검사를 검토한 후 해당 티켓 한 건의 HANDOFF로 --dispatch 대신 --complete ASSIGNMENT를 호출한다. 변경 커밋과 체크포인트가 확인되면 배정이 해제된다. 중단된 배정은 작업 브랜치와 진행 기록을 대조해 복구한다. 기존 CLI 배치에서 전환할 때는 진행 중인 프로세스를 먼저 정리한다.


## 이슈에서 MR로 전환

- 요구사항과 설계는 ITSM 이슈에서 관리한다. 설계 산출물 커밋을 검토한 담당자가 이슈의 `design-signoff` 요청에 승인하면 디스패처가 티켓 브랜치를 푸시하고 Draft MR을 만든다. 이슈와 MR은 서로 연결된다.
- 구현이 끝나면 디스패처가 같은 브랜치에 구현 커밋을 푸시한다. 테스트와 리뷰도 원 요청 이슈에서 Status를 확인한다. 리뷰 완료 후 Draft 표시가 해제되며 담당자가 GitLab에서 검토하고 병합한다.
- 배포는 배포 옵션을 켠 경우에 실행한다. MR 병합 상태, 검증된 소스 SHA, 대상 브랜치에 병합 SHA가 포함됐는지 확인한다. 병합 SHA의 전용 워크트리에서 테스트를 다시 실행하고 배포 승인을 받은 해당 SHA를 워커에 넘긴다.
- Git 푸시·페치는 운영 PC의 Git HTTPS 인증을 사용한다. GitLab API 토큰에는 MR과 댓글 읽기·쓰기 권한이 필요하다. MR 대상 브랜치는 GitLab 프로젝트 기본 브랜치이며 `dispatch.target_branch`로 지정할 수 있다.
- GitLab Premium·Ultimate의 최상위 그룹에서 이슈에 사용할 `검토 대기`와 `검토 완료`를 모두 In progress 범주로 등록한다. 각 검토를 시작할 때 자동화가 이슈의 Status를 `검토 대기`로 변경한다. 지정 담당자가 원 요청 이슈의 Status에서 `검토 완료`를 선택하면 다음 배치가 현재 상태와 GitLab의 시스템 기록에 남은 변경자를 확인한다.

## 단계별 산출물

| 단계 | Markdown 파일 | GitLab 위치 |
|---|---|---|
| 분석 | `requirements.md` | 요청 이슈 |
| 설계 | `design.md` | 요청 이슈 |
| 구현 | `implementation.md` | 요청 이슈와 MR |
| 테스트 | `test-results.md` | 요청 이슈와 MR |
| 리뷰 | `review.md` | 요청 이슈와 MR |
| 배포 | `release.md` | 요청 이슈와 MR |

워커는 배정 결과의 `report_path`에 Markdown을 작성한다. 분석·설계·구현 보고서는 요청 브랜치의 `artifacts/vibeops/`에 커밋한다. 단계 완료 호출 시 브랜치를 푸시하고 이슈에 검토 대상 커밋의 파일 링크를 남긴다. 설계 검토 요청에도 같은 링크를 표시한다. 테스트·리뷰·배포 보고서는 작업 트리 밖에서 작성하며, 완료 시 GitLab 프로젝트 첨부로 올리고 검증 대상 커밋과 함께 연결한다. 메인은 보고서 내용이 해당 프로젝트에 공유 가능한지 확인한 후에만 완료를 호출한다.
